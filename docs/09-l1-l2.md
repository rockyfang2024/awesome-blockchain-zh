# L1、L2 与扩容：开发者参考

本页用于理解常见架构名词并找到协议文档，不对链做性能、TVL 或安全排名。吞吐量、确认时间和费用受交易类型、网络负载、统计口径和时间窗口影响；引用单一 TPS 数字容易误导。

## 先分清这些类别

| 类别 | 它解决的问题 | 阅读入口 |
|---|---|---|
| L1 / 基础层 | 共识、数据可用性与状态执行由基础网络承担 | [Ethereum 开发者文档](https://ethereum.org/developers/docs/) · [Bitcoin 开发者文档](https://developer.bitcoin.org/) · [Solana 文档](https://solana.com/docs) |
| Rollup | 在链下执行，再把数据或证明提交给结算层；具体安全属性取决于实现和配置 | [Ethereum scaling](https://ethereum.org/layer-2/) · [L2BEAT 风险框架](https://l2beat.com/scaling/summary) |
| 状态通道 | 参与方在链下多次更新状态，按需回到链上结算 | [Lightning Developer Guide](https://docs.lightning.engineering/) |
| 侧链 / 独立链 | 有自己的共识与安全假设，通过桥或其他机制连接 | 阅读目标网络和桥的官方文档，分别核对验证者、退出和升级机制 |
| 应用链 / 模块化架构 | 针对应用定制执行或数据层；安全依赖其选择的结算、共识和数据可用性组件 | [Cosmos 文档](https://docs.cosmos.network/) · [Polkadot 文档](https://docs.polkadot.com/) |

## 读 L2 时重点核对

- **结算与数据可用性**：交易数据/状态承诺发布在哪里，用户在运营方失联时能否自行退出？
- **证明与争议机制**：有效性证明或欺诈证明是否已上线，谁能提交/挑战，等待期多长？
- **升级权限**：谁控制升级密钥，是否有多签、时间锁或紧急暂停权限？
- **排序器与桥**：是否单一排序器，故障时有哪些替代路径；桥的验证者和资产托管方式是什么？
- **当前状态**：使用 L2BEAT 等风险框架时，查看更新时间和具体指标；标签不是安全认证。
